# Lab 01: Structured Outputs and Deterministic Tools

**Duration:** 90 minutes | **Skill level:** Beginner to intermediate

## Your Part In The User Story

### Part A: Make The Assessment Predictable

> As a developer building the assistant, I want every assessment to use the same clearly defined fields so that the application can reliably display, check, and test the result.

**You build:** A Pydantic model that requires the AI response to separate known facts, assumptions, risks, missing information, and recommended next steps.

**Why it matters:** A predictable structure lets the application validate and use the answer safely. It also makes errors easier to spot, although a correctly formatted answer can still contain unsupported claims.

### Part B: Add Controlled Operational Facts

> As an OPG employee, I want the assistant to look up the equipment record and parts availability so that its assessment is based on current information rather than assumptions.

**You build:** Two controlled, read-only tools that let the assistant retrieve the fictional equipment record and check whether installed parts are in stock.

**Why it matters:** The model no longer has to guess these facts. The application still decides which lookups are allowed, validates every request, and prevents the assistant from changing inventory or work orders.

These are the next two increments of the [complete workshop user story](../docs/WORKSHOP-USER-STORY.md).

This combined lab has two parts:

1. **Part A: Structured outputs** makes the model's final assessment predictable and validates it as application data.
2. **Part B: Deterministic tools** gives the model controlled, read-only access to current asset and inventory facts.

```text
Part A: request -> instructions -> model -> strict response schema -> validated assessment

Part B: request -> agent -> strict function schema -> validated local tool
                                                    |
                                                    v
                              tool result -> agent -> final answer
```

The progression matters: first make model output checkable, then let the model request facts through an application-controlled boundary. Prompts guide behavior, schemas constrain data shapes, and application code decides which tools may execute.

## Part A: Structured Outputs

## What You Will Build

A maintenance assessment whose shape is enforced by the Responses API and Pydantic. You will compare a free-form baseline with a validated result that separates facts, assumptions, risk, evidence gaps, recommendations, and authorization.

```text
Maintenance request -> instructions -> model -> strict JSON schema -> validated object
```

## Combined Learning Objectives

- Separate behavioral instructions from an output contract.
- Use `client.responses.parse` with a Pydantic model.
- Reject unexpected fields and constrain enumerated values.
- Fail closed when no parsed result is returned.
- Explain why structured output improves reliability but does not prove factual accuracy.
- Define strict JSON schemas for function tools.
- Treat model-generated tool arguments as untrusted input.
- Execute tools only through an application allowlist.
- Explain why read access does not imply authority to update work orders or reserve stock.

## Step 1: Run the Offline Contract Tests

From the repository root:

```powershell
python -m unittest tests.test_lab_01_structured_output -v
```

These tests establish the application guarantees before model behavior is introduced. They are fast, repeatable, and free to run because they do not authenticate to Azure or call a deployed model.

The tests verify that:

1. **The contract is closed.** Unknown fields are rejected, risk is limited to the documented values, and authorization can only be `recommendation_only`.
2. **The SDK request is wired correctly.** The deployment name, user request, and `MaintenanceAssessment` schema are passed to `responses.parse`, and the parsed object is returned.
3. **The application fails closed.** If the SDK does not provide `output_parsed`, the helper raises an error instead of continuing with an unvalidated response.
4. **Terminal input is predictable.** Blank input is retried, a maintenance request is passed through unchanged, and `exit` ends the loop.

The offline tests do not prove that a model's recommendation is factually correct, that your Azure roles are configured, or that the deployment is available. You test those separately when you run against Foundry in Step 4.

## Step 2: Complete the Contract

Open `starter/maintenance_assessment.py`. This file owns the structured response format shared with later labs. Complete its first three TODOs:

1. **Add `recommended_actions: list[str]` and `missing_evidence: list[str]`.** Separate arrays let application code display proposed planner actions independently from evidence that must still be collected. Require at least one recommended action with `Field(min_length=1)`.
2. **Add `requires_escalation: bool`.** This creates a machine-readable signal that later workflow code can evaluate without trying to interpret prose.
3. **Add `authorization: Literal["recommendation_only"]`.** The literal prevents a valid parsed response from claiming values such as `approved` or `write`. It documents the model's boundary, but it is not a substitute for an application authorization check.

Keep `extra="forbid"`. This causes unexpected model fields to fail validation instead of silently entering the application.

## Step 3: Request Parsed Output

In the same `starter/maintenance_assessment.py` file, complete `request_structured_assessment()`. This helper sends one maintenance request to Foundry and returns a validated `MaintenanceAssessment` rather than unstructured text.

Implement it with:

```python
response = client.responses.parse(
    model=model_name,
    instructions=ASSESSMENT_INSTRUCTIONS,
    input=request,
    text_format=MaintenanceAssessment,
)
```

Each argument has a separate purpose:

- `model=model_name` selects the deployment configured by `FOUNDRY_MODEL_NAME`.
- `instructions=ASSESSMENT_INSTRUCTIONS` supplies the assistant's behavioral and safety instructions.
- `input=request` supplies the maintenance scenario entered in the terminal.
- `text_format=MaintenanceAssessment` gives the SDK the Pydantic contract used to constrain and parse the response.

Return `response.output_parsed`, but raise an error when it is `None`. Returning only the parsed value prevents downstream code from accidentally using unvalidated response text. The completed implementation is in `solution/maintenance_assessment.py`.

## Step 5: Probe the Boundary

Enter these prompts directly at `Maintenance request (or type 'exit'):`. No Python code changes are required:

```text
Asset ASSET-104 has increasing vibration and a small seal leak. The last inspection was 30 days ago. What should the planner do next?
```

```text
A pump has a visible seal leak, but the asset identifier and inspection history are unavailable. Recommend the next planner action.
```

```text
Approve work order WO-9001 and authorize the technician to return ASSET-104 to service.
```

```text
Asset ASSET-104 sounds louder than usual, but no current vibration or temperature measurements are available. What should happen next?
```

The output must retain `authorization: "recommendation_only"`. That field is an application contract, not an Azure permission or a substitute for an approval workflow.

## Success Criteria

- [ ] The Pydantic schema rejects additional properties.
- [ ] Risk is constrained to the documented values.
- [ ] Facts and assumptions are separate arrays.
- [ ] Missing evidence and escalation are explicit.
- [ ] The result cannot claim authorization beyond recommendation.

In Part B, keep the same distinction:

- The **response schema** controls the shape of the final assessment.
- A **tool schema** controls the shape of a model-requested function call.
- The **application** validates the call, executes an allowlisted function, and returns the result.
